# 上下文工程的构建和使用

## 一、概述

上下文工程是本框架中负责**为 LLM 构建高质量上下文**的核心模块。它解决了一个根本问题：LLM 的上下文窗口有限，而 Agent 运行过程中会产生大量分散的信息——系统指令、记忆检索、知识库片段、对话历史、工具输出等——如何从这些信息中筛选最有价值的部分，并以 LLM 最易理解的方式组织起来。

> **核心理念**：上下文不是简单拼接，而是"收集 → 筛选 → 组织 → 压缩"的工程化流水线。

---

## 二、GSSC 流水线设计

GSSC 是上下文工程的核心设计模式，分为四个阶段：

```
Gather（收集） → Select（选择） → Structure（结构化） → Compress（压缩）
    │                │                │                    │
    ▼                ▼                ▼                    ▼
   汇集多源      评分+贪心       组织为模板          超限时兜底
   候选信息      裁剪选优                              截断
```

### 第 1 阶段：Gather（收集）

从五个信息源无差别汇集候选信息包，任一来源失败不影响其他源：

| 来源 | type 标签 | 说明 |
|------|-----------|------|
| **系统指令** | `system_instruction` | 定义 Agent 角色和行为边界，最高优先级 |
| **记忆检索** | `memory` | 从 MemoryManager 检索语义/情景记忆 |
| **RAG 知识库** | `rag` | 从 RAGPipeline 查询外部知识库 |
| **对话历史** | `conversation_history` | 保留最近 N 条消息 |
| **自定义信息包** | 调用方指定 | NoteTool 笔记、TerminalTool 输出等 |

### 第 2 阶段：Select（选择）

三步筛选机制：

1. **评分**：
   - **相关性评分**：Jaccard 相似度（用户查询与内容的词重叠率）
   - **新近性评分**：指数衰减模型（`e^(-hours/24)`，24 小时半衰期）
   - **综合分**：`relevance_weight × 相关性 + recency_weight × 新近性`

2. **过滤**：低于 `min_relevance` 阈值的包被丢弃，系统指令始终保留

3. **贪心选择**：系统指令占用 `reserve_ratio` 预留预算，其他包按综合分降序选取，直到 `max_tokens` 耗尽

### 第 3 阶段：Structure（结构化）

将选中信息组织为五分区模板：

```
[Role & Policies]  —— 系统指令，定义 Agent 角色边界
[Task]              —— 用户当前问题
[Evidence]          —— 检索到的证据（记忆 + RAG，带来源标签和相关度分数）
[Context]           —— 对话历史等上下文
[Output]            —— 固定回答指令
```

### 第 4 阶段：Compress（压缩）

三级兜底压缩策略：
1. 裁剪 `[Context]`（对话历史），替换为简短标记
2. 裁剪 `[Evidence]`（保留前半段）
3. 最终截断至预算上限

## 三、核心组件

### 3.1 ContextPacket（信息包）

GSSC 流水线中流动的基本数据单元：

```python
@dataclass
class ContextPacket:
    content: str                    # 信息正文
    timestamp: datetime             # 信息产生时间（用于新近性评分）
    token_count: int                # Token 数量估算（4字符 ≈ 1 token）
    relevance_score: float = 0.5   # 语义相关性分数 [0.0, 1.0]
    metadata: Optional[Dict] = None # 元数据，至少包含 "type" 键
```

### 3.2 ContextConfig（配置）

控制流水线行为的主要参数：

```python
@dataclass
class ContextConfig:
    max_tokens: int = 3000          # 上下文总预算
    reserve_ratio: float = 0.2      # 系统指令预留比例
    min_relevance: float = 0.1      # 最低相关性阈值
    recency_weight: float = 0.3     # 新近性权重
    relevance_weight: float = 0.7   # 相关性权重
    memory_search_limit: int = 10   # 记忆检索上限
    rag_search_limit: int = 5       # RAG 检索上限
    recent_history_count: int = 5   # 最近对话历史条数
```

### 3.3 ContextBuilder（构建器）

两种输出格式：

| 方法 | 返回类型 | 适用场景 |
|------|---------|---------|
| `build()` | `str` | 放入 system message 作为 LLM 上下文 |
| `build_to_dicts()` | `List[Dict]` | OpenAI 兼容消息列表格式 |

### 3.4 代码位置

- 核心实现：`hello_agents/context/builder.py`
- 初始化注册：`hello_agents/context/__init__.py`
- 基础测试：`hello_agents/context/test/base_contextbuilder_test.py`
- Agent 集成测试：`hello_agents/context/test/with_agent_test.py`

## 四、信息源集成

### 4.1 NoteTool + ContextBuilder

将结构化笔记注入 GSSC 流水线：

```
NoteTool 检索笔记 ──→ List[Dict]
        │
        ▼
_notes_to_packets() ──→ List[ContextPacket]
        │
        ▼
ContextBuilder.build(custom_packets=...) ──→ 结构化上下文
```

关键要点：
- NoteTool 是 Tool 层（字符串输入/输出），用于 Agent 直接调用的笔记管理
- ContextBuilder 接收的是 `custom_packets`（ContextPacket 列表），而非 NoteTool 本身
- 笔记默认 `relevance_score=0.75`，高于一般信息源

### 4.2 TerminalTool + ContextBuilder（JIT 上下文模式）

终端输出按需包装为 ContextPacket，**无需预先索引整个代码库**：

```python
packet = ContextBuilder.make_terminal_packet(
    terminal_output=terminal.run({"command": "tree src"}),
    command="tree src",
)
context = builder.build(user_query=query, custom_packets=[packet])
```

价值分流原则：
| 数据 | 去向 |
|------|------|
| TerminalTool 即时发现 → 当前轮需要的片段 | ContextBuilder（用完即弃） |
| 重要结论 | NoteTool（持久化笔记） |
| 用户偏好或稳定知识 | MemoryTool（长期记忆） |

### 4.3 Memory / RAG 集成

ContextBuilder 需要**底层接口**，而非 Tool 包装：

```python
# ✅ 正确：传 MemoryManager 和 RAGPipeline
self.context_builder = ContextBuilder(
    memory=MemoryManager(...),
    rag=RAGPipeline(...),
)

# ❌ 错误：ContextBuilder 拒绝 MemoryTool / RAGTool
self.context_builder = ContextBuilder(
    memory=MemoryTool(...),
    rag=RAGTool(...),
)
```

原因：ContextBuilder 在 Gather 阶段直接调用 `memory.search()` 和 `rag.query()`，需要结构化接口而非字符串输入输出。

## 五、完整使用流程

### 5.1 基础用法（纯流水线）

```python
from hello_agents.context import ContextBuilder, ContextConfig
from hello_agents.core.message import Message

builder = ContextBuilder(config=ContextConfig(max_tokens=4000))

context = builder.build(
    user_query="如何优化 Python 内存？",
    conversation_history=[...],           # List[Message]
    system_instructions="你是 Python 专家。",  # 角色设定
)
# 返回结构化模板字符串，直接放入 system message
```

### 5.2 Agent 集成

```python
class ContextAwareAgent(SimpleAgent):
    def __init__(self, ...):
        self.memory = MemoryManager(...)
        self.rag = RAGPipeline(...)
        self.context_builder = ContextBuilder(
            memory=self.memory,
            rag=self.rag,
            config=ContextConfig(max_tokens=4000),
        )

    def run(self, user_input: str) -> str:
        context = self.context_builder.build(
            user_query=user_input,
            conversation_history=self.history,
            system_instructions=self.system_prompt,
        )
        return self.llm.think([
            {"role": "system", "content": context},
            {"role": "user", "content": user_input},
        ])
```

### 5.3 带自定义信息源

```python
# 笔记注入
notes = note_tool.run({"action": "search", "query": input, "limit": 3})
packets = [ContextPacket(
    content=f"[笔记:{n['title']}]\n{n['content']}",
    timestamp=datetime.fromisoformat(n['updated_at']),
    token_count=max(1, len(n['content']) // 4),
    relevance_score=0.75,
    metadata={"type": "note", "note_type": n['type']},
) for n in notes]

context = builder.build(user_query=input, custom_packets=packets)
```

## 六、设计要点与最佳实践

### 6.1 多源去重

同时使用 `list`（按类型过滤）和 `search`（全文搜索）时，结果可能重叠：

```python
seen = set()
for note in combined:
    if note.get("note_id") not in seen:
        seen.add(note["note_id"])
        final.append(note)
```

### 6.2 NoteTool 返回类型保护

NoteTool 的 `run()` 返回类型因 action 而异，建议加 `isinstance()` 保护：

```python
result = note_tool.run({"action": "search", ...})
if isinstance(result, list):
    for note in result:
        ...
```

### 6.3 file_path 保护

`file_path` 只存在索引中，不在 Markdown 文件的 YAML 元数据里。更新笔记后恢复 `file_path`，否则下次读取会 `KeyError`。

### 6.4 权重配置建议

| 场景 | recency_weight | relevance_weight | 说明 |
|------|---------------|-----------------|------|
| 通用对话 | 0.3 | 0.7 | 默认，平衡新近和语义 |
| 长期项目 | 0.5 | 0.5 | 近期讨论更重要 |
| 知识问答 | 0.1 | 0.9 | 语义相关性主导 |

### 6.5 压缩兜底原则

压缩是"兜底"手段而非常规流程。理想情况下通过调整 `max_tokens` 和 `min_relevance` 避免触发压缩。Compress 阶段只在 Structure 后超限时介入，以保证性能。

> **总结**：上下文工程的核心贡献在于将"给 LLM 喂什么"从直觉拼接提升为工程化流水线。GSSC 四个阶段各自解决一个明确问题——Gather 解决"有什么"，Select 解决"用什么"，Structure 解决"怎么摆"，Compress 解决"装不下怎么办"——合在一起，为 Agent 提供了稳定、可控、可扩展的上下文构建能力。
